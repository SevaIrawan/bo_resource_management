Wireframe Review and Change Breakdown

Comparison of application structure: Version 1.0.30 and Proposed Version. Implementation, testing, and publication require HOD approval.

1. Key change points

Point 01 Main tabs from three to two

Change

  1. Reporting tab removed.
  2. Remaining tabs: Account and Operations.

Rationale: Three tabs fragmented the daily workflow.

Point 02 Account as the centre for monitoring and decisions

Change

  1. Stock status moved to the brand card in Account.
  2. Group matrix opened from the brand card in Account.

Rationale: Operational decisions must sit next to the brand-account context under review.

Point 03 Sequential Job Queue task pairing

Change

  1. Create Group and Set Photo — after create completes, Set Photo is queued automatically when a brand photo is available.
  2. Leave and Delete — after leave completes, Delete is queued automatically only for groups successfully left.
  3. Photo in Create Group modal — no photo: Upload Photo (required before Queue). Photo exists: Preview Photo; Queue allowed.

Rationale: Sequential tasks are combined. Photo is requested at Create Group, not when adding a brand.

Point 04 Operations focused on the Job Queue

Change

  1. Operations opens directly to the Job Queue.
  2. Leave/Delete Queue without display disruption.
  3. Leave failure reasons shown in Remark.

Rationale: Execution UI must be stable; failures must be auditable.

Point 05 Device execution resilience

Change

  1. Telegram scrape — quality gate that stopped scrapes due to many zero member counts is removed; member count and invite links prioritise complete server data.
  2. Telegram automation — session lock fixed so create/automation jobs do not deadlock.
  3. WhatsApp Leave — retries, fallback paths, and failure reason in Remark.

Rationale: Layout changes are insufficient if device execution still fails without a documented reason.

2. Point 03 edge cases

Scenario System behaviour Operator follow-up
Create Group with no brand photo Modal shows Upload Photo. Queue blocked until upload succeeds. Upload in Create Group modal. After create completes, Set Photo is queued automatically.
Create done; Set Photo needs retry Set Photo can still be queued manually from create VIEW. Open create VIEW → Queue Set Photo (when brand photo is available).
Leave succeeded (status left) Delete queued automatically only for groups with status left. Monitor Delete queue; intervene only if Delete fails.
Leave failed Failed groups are not auto-deleted. Status and reason shown in Remark. Fix cause → re-run Leave from queue/VIEW. No automatic Delete for groups not left.

4. Success metrics (KPI)

  1. Navigation (Point 01). Daily work through two tabs (Account · Operations). Reporting removed.
  2. Account (Point 02). Stock and matrix available from the Account brand card.
  3. Job Queue (Point 03). Create→Set Photo and Leave→Delete automatic under stated conditions (see section 2).
  4. Operations (Point 04). Focused on Job Queue; Queue without display disruption; failure reason in Remark.
  5. Device (Point 05). Telegram scrape/automation more reliable; WhatsApp Leave has fallback and Remark. Optional post-release: compare manual interventions before vs after.

Sequence: Job Queue → device tests → document → HOD approval → publication.

6. Business arguments

  1. Status quo — navigation. Work split across Reporting, stock Overview, and Job Queue; adds time and brand-context errors.
  2. Status quo — Create and Set Photo. After create, Set Photo remains manual from VIEW; easy to miss.
  3. Status quo — Leave and Delete. After leave, Delete remains manual; easy to miss at high volume.
  4. Status quo — failures without reason. Leave failures without Remark slow remediation.
  5. Proposed Version. Monitor and decide in Account; execute in Operations; sequential flows automated under conditions; failures auditable.

7. Risks and rollback

  1. Risk: Auto Set Photo / Auto Delete runs under the wrong condition.
    Mitigation: Set Photo only when photo available; Delete only for left status; Remark for audit.
  2. Risk: Operators unfamiliar without the Reporting tab.
    Mitigation: Matrix remains on Account brand card; short release briefing.
  3. Operational rollback: Auto follow-up can be disabled without reverting full structure. Create→Photo and Leave→Delete remain available manually from VIEW.
  4. UI rollback (Reporting / Overview): Only if approval requires it; higher cost. Evaluate KPI before rolling back tab structure.
