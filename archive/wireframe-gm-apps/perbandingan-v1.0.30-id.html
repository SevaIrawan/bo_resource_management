Tinjauan Wireframe dan Uraian Perubahan

Perbandingan struktur aplikasi Versi 1.0.30 dan Versi Usulan. Implementasi, pengujian, dan publikasi menunggu persetujuan HOD.

1. Poin utama perubahan

Poin 01 Tab utama dari tiga menjadi dua

Perubahan

  1. Tab Reporting dihapus.
  2. Tab tersisa: Account dan Operations.

Alasan: Tiga tab memecah alur kerja harian.

Poin 02 Account sebagai pusat pantauan dan keputusan

Perubahan

  1. Status stock dipindah ke kartu brand di Account.
  2. Matrix grup dibuka dari kartu brand di Account.

Alasan: Keputusan operasional harus dekat dengan kondisi akun brand yang dikerjakan.

Poin 03 Penggabungan tugas Job Queue berurutan

Perubahan

  1. Create Group dan Set Photo — setelah create selesai, Set Photo masuk antrian otomatis jika foto brand tersedia.
  2. Leave dan Delete — setelah leave selesai, Delete masuk antrian otomatis hanya untuk grup yang berhasil ditinggalkan.
  3. Foto di modal Create Group — tanpa foto: Upload Photo (wajib sebelum Queue). Ada foto: Preview Photo; Queue diizinkan.

Alasan: Tugas berurutan digabung. Foto diminta saat Create Group, bukan saat menambah brand.

Poin 04 Operations difokuskan pada Job Queue

Perubahan

  1. Tab Operations menampilkan Job Queue secara langsung.
  2. Proses Queue Leave/Delete tanpa gangguan tampilan.
  3. Alasan kegagalan Leave ditampilkan di Remark.

Alasan: Antarmuka eksekusi harus stabil; kegagalan harus dapat diaudit.

Poin 05 Ketahanan eksekusi perangkat

Perubahan

  1. Telegram scrape — quality gate yang menghentikan scrape karena banyak member count 0 dihapus; member count dan invite link mengutamakan data lengkap dari server.
  2. Telegram otomasi — kunci sesi diperbaiki agar job create/otomasi tidak saling mengunci hingga hang.
  3. WhatsApp Leave — percobaan ulang, jalur cadangan, dan alasan gagal di Remark.

Alasan: Perubahan struktur layar tidak cukup jika eksekusi perangkat masih gagal tanpa alasan yang terdokumentasi.

2. Edge case Point 03

Skenario Perilaku sistem Tindak lanjut operator
Create Group tanpa foto brand Modal menampilkan Upload Photo. Queue diblokir sampai upload berhasil. Upload di modal Create Group. Setelah create selesai, Set Photo masuk antrian otomatis.
Create selesai; Set Photo perlu diulang Set Photo tetap dapat di-queue manual dari VIEW create. Buka VIEW create → Queue Set Photo (jika foto brand tersedia).
Leave berhasil (status left) Delete masuk antrian otomatis hanya untuk grup berstatus left. Pantau antrian Delete; intervensi hanya jika Delete gagal.
Leave gagal Grup gagal tidak masuk Delete otomatis. Status dan alasan ditampilkan di Remark. Perbaiki penyebab → jalankan ulang Leave dari antrian/VIEW. Tidak ada Delete otomatis untuk grup yang belum left.

4. Tolok ukur keberhasilan (KPI)

  1. Navigasi (Poin 01). Kerja harian lewat dua tab (Account · Operations). Reporting dihapus.
  2. Account (Poin 02). Stock dan matrix tersedia dari kartu brand Account.
  3. Job Queue (Poin 03). Create→Set Photo dan Leave→Delete otomatis sesuai syarat (lihat bagian 2).
  4. Operations (Poin 04). Fokus Job Queue; Queue tanpa gangguan tampilan; alasan gagal di Remark.
  5. Perangkat (Poin 05). Scrape/otomasi Telegram lebih andal; Leave WhatsApp punya jalur cadangan dan Remark. Opsional pasca-rilis: bandingkan intervensi manual sebelum vs sesudah.

6. Argumen bisnis

  1. Status quo — navigasi. Kerja terpecah ke Reporting, Overview stock, dan Job Queue; menambah waktu dan risiko salah konteks brand.
  2. Status quo — Create dan Set Photo. Setelah create, Set Photo masih manual dari VIEW; mudah terlewat.
  3. Status quo — Leave dan Delete. Setelah leave, Delete masih manual; mudah terlewat pada volume tinggi.
  4. Status quo — kegagalan tanpa alasan. Leave gagal tanpa Remark memperlambat perbaikan.
  5. Versi Usulan. Pantauan dan keputusan di Account; eksekusi di Operations; alur berurutan otomatis sesuai syarat; kegagalan dapat diaudit.

7. Risiko dan rollback

  1. Risiko: Auto Set Photo / Auto Delete berjalan pada kondisi yang tidak diinginkan.
    Mitigasi: Set Photo hanya jika foto tersedia; Delete hanya untuk status left; Remark untuk audit.
  2. Risiko: Operator belum terbiasa tanpa tab Reporting.
    Mitigasi: Matrix tetap dari kartu brand Account; briefing singkat saat rilis.
  3. Rollback operasional: Auto follow-up dapat dinonaktifkan tanpa mengembalikan seluruh struktur. Create→Photo dan Leave→Delete tetap dapat dijalankan manual dari VIEW.
  4. Rollback UI (Reporting / Overview): Hanya jika diminta approval; biaya lebih tinggi. Evaluasi KPI sebelum rollback struktur tab.
